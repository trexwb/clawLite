# 自检与发布流程

## 一、改动后必须做的事

任何代码 / 脚本 / 配置改动，落地前都要过这三道：

```bash
npm run check          # 静态自检，必须全绿
npm run build          # 主进程 + 渲染层构建
npm run verify:dist    # 构建产物校验（需先 build:web，npm run build 已含）
```

## 二、静态自检 `npm run check`（`scripts/check.ts`）

| 校验项 | 内容 |
|---|---|
| 基础合法性 | JSON 合法性、关键文件存在性 |
| 源码形态 | 源码后缀门禁（`electron/`、`scripts/`、`src/` 无残留 `.cjs` / `.mjs` / `.js`）+ `tsc --noEmit` 类型检查 |
| IPC 契约 | **三层对齐**：渲染层 `api.*` → preload 暴露方法 → 主进程 `ipcMain.handle` 通道 / 广播事件 |
| 运行时 | 内置 DSH 运行时完整性（入口与版本） |
| 依赖 | 无残留 Tauri 依赖 |
| 状态机 | **状态枚举双向可达**：`setState` 取值 ↔ 渲染层 `STATE_LABEL`，多出来的即死枚举 |
| 样式 | **日志着色类名 ↔ CSS 交叉**：同时拦死样式与死类名 |
| 端口 | **端口范围三方一致**：`index.html` ↔ `src/shared/constants.ts` ↔ `harness.ts`（1024–65535） |
| 安全与无障碍 | `webPreferences` 逐块断言、CSP 脚本侧未放宽、`connect-src` 仅 `'self'`、播报区唯一 |
| 产物形态 | 主进程产物必须 ESM（有 `import` 无 `require`）、preload 产物必须 CJS |

> 本地未拉取内置 DSH 运行时时会出现 1 项 WARN，属预期，与代码改动无关。

## 三、产物校验 `npm run verify:dist`（`scripts/verify-dist.ts`）

静态自检看不到构建产物，因此单独一道：

- 断言 `dist/index.html` 的资源引用为相对路径（`base: './'` 未被动过）；
- 断言品牌图标资产真实产出到 `dist/assets/` 且被引用。

## 四、打包

```bash
npm run dist:mac       # macOS：dmg + zip
npm run dist:win       # Windows：NSIS 安装器
npm run dist:linux     # Linux：AppImage
npm run dist           # 当前平台
```

产物输出到 `release/`。

### 代码签名状态（当前：未签名）

CI 与本地打包一致，均为**未签名版本**，可正常出包与分发：

- `release.yml` 的打包步骤与本地打包都显式设置 `CSC_IDENTITY_AUTO_DISCOVERY=false`，关闭 electron-builder 的证书自动发现；
- 未配置任何签名凭据，因此不存在「因证书缺失导致打包失败」的风险；
- 代价是 macOS 产物未签名 / 未公证，首次打开需右键「打开」绕过 Gatekeeper（详见 [[常见问题]]）。

### 启用 macOS 代码签名 + 公证

`release.yml` 已把所需配置以**注释占位**形式预留，secrets 到位后照下面四步做即可生效（**无需改 `electron-builder.yml`**）：

| 步骤 | 操作 |
|---|---|
| 1 | 仓库 `Settings → Secrets and variables → Actions` 添加 5 个 secrets：`CSC_LINK`、`CSC_KEY_PASSWORD`、`APPLE_ID`、`APPLE_APP_SPECIFIC_PASSWORD`、`APPLE_TEAM_ID` |
| 2 | 删除打包步骤 env 中的 `CSC_IDENTITY_AUTO_DISCOVERY: "false"` 行（**必须删除**：该开关会关闭证书自动发现，不删则证书不被使用，产物仍是未签名） |
| 3 | 取消该段中各项 secrets 的注释 |
| 4 | 推送 `v*` tag 验证：日志应出现签名与 `notarization successful`，产物用 `codesign -dv --verbose=4`、`spctl -a -vv` 复核 |

要点：

- 证书须为 **Developer ID Application**；`electron-builder.yml` 的 `mac` 段已备好 `hardenedRuntime: true` 与 `entitlements`，无需改动；
- electron-builder 在检测到 `APPLE_ID` + `APPLE_APP_SPECIFIC_PASSWORD` + `APPLE_TEAM_ID` 三者齐全时自动走 `notarytool` 公证（缺任一即报错），不需要额外写 `notarize` 配置；
- Windows 代码签名用另一组变量（`WIN_CSC_LINK` / `WIN_CSC_KEY_PASSWORD`），如需一并启用请另加，当前不启用；
- 文档中「未签名」的表述须与 `release.yml` 实际状态保持同步，启用后一并更新 README「已知限制」与本页。

## 五、CI 流水线

`.github/workflows/release.yml`：推送 `v*` tag（或手动触发）后，在 macOS / Windows runner 上分别执行

```
npm ci → npm run runtime → npm run check → npm run build:web → npm run verify:dist → electron-builder
```

产物汇总后由 `publish` job 创建 GitHub Release。**能过 CI 的产出才算完成。**

## 六、版本纪律与发布日志

- 版本号单一来源：`package.json` 的 `version`；`electron-builder` 产物名、`app.getVersion()`、`app:info` 均读此值。
- **正式发布后按语义化版本（SemVer）正常迭代**：不向后兼容的破坏性变更 → 主版本；向后兼容的新功能 / 新能力 → 次版本；向后兼容的修复、体验打磨、文档 / 样式等非功能性改动 → 修订号（v1.0.1 即首个发布后修订号）。
- 发布前的 v1.0.0 基线阶段口径更严：末位 +1 仅限「不同类、不同根因的新功能 / 新修复」且用户明确允许，同日同模块追加修复、仅文档更新、纯 CSS / 文案打磨一律不推进版本号。
- 每次迭代都要写日志：追加到 `docs/version/RELEASE-v{主版本}.md` 顶部新分节，标注日期与版本号（用户明确要求不改版本号时注明「不推进版本号」）；历史日志只增不改。
- 内置 DSH 运行时版本由 `scripts/fetch-runtime.ts` 的 `DSH_VERSION` 决定，与应用版本独立；内置 DSH 依赖树自身的 `package.json` 的 `version` 同样不属于应用版本，不得随应用版本改动。
